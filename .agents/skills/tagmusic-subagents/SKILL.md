# Tag Music 成果批次协作

## 作用域与恢复

- 仅用于解析后的项目根 `D:\.projects\Tag Musicplayer` 及子目录，不改全局 subagents。开发、修复、测试按本 Skill 协作；子 Agent 只执行分配任务，不再派发或联系其他聊天。
- 恢复、阶段确认/Goal、暂停、设备授权、失败处理、状态和记录统一遵守 [AGENTS.md](../../../AGENTS.md)。先读 [HANDOFF](../../../docs/HANDOFF.md)，核对实际分支、工作区和相关提交，再读本批必要入口。读取 Skill 不代表恢复暂停阶段。
- 主 Agent 负责目标、批次、进度、授权、资源与收口，默认由一个 developer 连续实现相关功能；主可直接维护流程文档和协调元数据，无需为此另建角色流水线。主按需读必要差异/结果核对交付，不把例行核对强制交独立 reviewer。

## 默认交付方式

- 每阶段列少量有完整使用价值的批次：完整页面、完整功能链或共享结构的相似页面组。已有明确需求和计划就直接交 developer，不重复调用 planner；歌单/标签/专辑等相似页面尽量一起完成。
- 一次派发交清交付目标、范围、必要入口、验收范围和完成条件。同批连续完成小功能，developer 自行处理调用方、格式、明显编译问题及必要调整；不逐按钮/逐页面走规划、测试、审查、记录、提交。
- 普通边界问题集中记入本批缺口并处理，不不断追加测试任务；重大目标/架构变化交用户确认。自动检查以发现明显编译错误及候选运行阻塞为主，页面组/功能链完成后集中一次必要检查，优先已有入口、只查相关范围。不默认新增测试文件或机械全量回归。
- 普通 UI、相似页面、文案和一般交互可由 developer 直接准备体验候选，不默认独立 reviewer。大部分界面/布局/体验交用户；按反馈定向修复，不扩展成无关测试工程。
- 进度按“已实现、正在实现、剩余”报告产品内容；每个可体验功能组优先交付，附新增内容、进入位置、操作/预期和已知缺口，不等整阶段完成或全部边界覆盖。实现完成、候选可运行、用户验收分别记录，未执行明确未测。

## 角色、配置与路由

可用角色为 `developer`、`planner`、`reviewer`、`command_runner`、`phone_tester`、`windows_tester`。仅在能并行独立实现、解决具体困难或降低明确风险时增加角色，不为分工完整凑流水线。新增岗位或 Skill 须先获用户授权；不影响复用既有角色处理明确任务。

[defaults.json](defaults.json) 是自定义请求配置的唯一来源，不是 Codex 原生配置。主期望 Luna/high 由用户界面选择，Skill 不证明实际模型；无可信元数据时实际配置记“未验证”。指定配置/工具不可用须报告，不静默替换。

| 工作项 | 配置/处理 |
|---|---|
| 单文件文档、明确的小 UI/文案变更 | developer / `simple`；流程文档主可直接维护 |
| 普通页面组、完整功能链及一般交互 | developer / `normal`，默认持续负责本批及反馈修复 |
| 数据丢失、数据库迁移、持久身份、SAF 授权/URI、播放并发/异步状态或 FD 生命周期的实际行为变化 | developer / `high_risk`，仅对具体风险做最小定向检查；需要独立判断时加 reviewer / `high_risk` |
| 需求/依赖确有待决、具体技术困难 | 按需 planner / `planner`，只解决当前问题 |
| 关键证据冲突、需独立判断的明确风险、用户要求独立审查 | reviewer / `high_risk` 或 `acceptance`，范围写清 |
| 需要分担的已有明确自动命令 | 按需 `command_runner`；developer 也可在资源排程内直接执行，不强制交接 |
| 手机明确 ADB 脚本/断言；复杂视觉操作 | `phone_script`；`phone_visual`，定位升级见[手机执行](references/roles.md#手机执行) |
| 电脑 GUI | `windows_gui`，必须 Windows MCP + `gpt-6.1-terra/high`，不可替换 |

developer 根据实际变化说明具体风险及对应检查，不因跨页面、普通公共 UI 组件或仅提及术语而升级。例行调用方调整不回 planner；确需改变配置先停旧执行者相关写入，保留失败累计，不扩大范围或设备授权。

## 派发与资源约束

- spawn 显式 `fork_turns: "none"`、model、reasoning_effort，task_name 仅小写字母/数字/下划线。只传本批目标、差异和必要入口；角色读 [roles.md](references/roles.md) 公共边界及自身小节，设备任务另读共同要求。
- 最多同时 3 个子 Agent；默认一个 developer，独立且无写入冲突的实现才并行。Flutter 检查、测试、构建全局串行，设备同一时刻一个控制者。
- 相关实现和明确反馈修复优先复用原 developer，不因一个小功能、一次检查、记录或提交完成就换 Agent。仅配置改变、需要真正独立审查、上下文失效或写入冲突时换人；失联不等于停写，先确认释放，失败累计不清零。reviewer 启用时不得参与被审实现。
- 使用有界等待；收到批次进展、完成或异常再处理，不短周期轮询、不重复读相同文件或重新规划。用户要求收尾/停止时立即停新增开发、测试和审查任务，保存现有成果、未测和未完成项，集中记录/检查点后交接停止，不补齐流程而扩展工作。

## 交付入口

默认：已有需求/计划 → 一个 developer 连续实现 → 批次必要检查与候选 → 用户体验 → 原 developer 定向修复。planner、command_runner 和 reviewer 均按实际需要插入，不是交付前置岗位。

回传按[短交接协议](references/handoff.md)，developer 可直接交 main 收口。每批集中更新当前计划进度、HANDOFF 和 Git 检查点；HANDOFF 引用稳定检查点，不追写自身最新 HEAD。完成摘要仅开发日志每批一行；详细输出/证据只保存一次，引用 `artifacts/Rxx/` 原入口。正式用户验收按项目索引记录，构建或自查不能冒充用户通过。
