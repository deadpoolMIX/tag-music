# Tag Music：双端本地音乐播放器开发计划

## 1. 已确认的目标与边界

采用 **Flutter + Material Design 3 + 成熟音频组件**，共用界面、标签、筛选及歌单逻辑，分别构建 Windows 和 Android 应用。首版两端数据独立。

- **平台**：Windows 10/11 x64、Android 10 及以上；优先验证当前电脑和你的手机。
- **规模**：一万首以内的本地音乐库。
- **音乐来源**：手动选择多个文件夹，递归扫描；Android 使用系统目录授权。
- **核心功能**：多标签管理、可视化嵌套筛选、临时播放队列、普通歌单、智能歌单。
- **日常功能**：封面、本地歌词、搜索排序、队列编辑、循环与随机播放、睡眠定时、后台播放及系统媒体控制。
- **数据安全**：自定义标签仅存应用数据库；音乐文件不被修改。文件失联时保留标签和歌单关联，支持重新定位。
- **暂不纳入**：云同步、音乐传输、联网歌词、流媒体、均衡器、无缝播放、CUE 分轨及加密音乐解密。

暂用名称 **Tag Music**，简体中文，支持深浅主题。采用本地 Git 管理，默认不创建公开远程仓库；原创代码使用 MIT 许可，第三方组件分别保留其许可要求。

Harmonoid 只作功能参考。其当前 PolyForm Strict 许可没有授予本项目所需的修改、衍生及再分发权利。[许可原文](https://github.com/harmonoid/harmonoid/blob/master/LICENSE)

## 2. 技术结构与关键行为

### 共用代码和平台适配

| 部分 | 确定方案 |
|---|---|
| 界面 | Flutter Material 3；手机底部导航，桌面侧栏导航；共用页面和业务逻辑 |
| 状态与数据 | Riverpod；Drift + SQLite；数据库迁移从第一版开始管理 |
| 播放引擎 | `media_kit` + 音频专用原生库，避免自行实现解码器 |
| 元数据 | `audio_metadata_reader`；封面按需读取、缩略和缓存 |
| Android | Kotlin 封装 SAF 目录访问；`audio_service`、`audio_session` 管理后台播放、通知和音频焦点 |
| Windows | 本地文件系统适配、`smtc_windows` 系统媒体控制、托盘和快捷键 |
| 构建 | PowerShell 7 脚本统一环境检查、测试和打包；工具链及依赖版本在 R0/R1 锁定 |

`media_kit` 已提供双端音频能力；`audio_service` 用于 Android 的后台与系统交互，Windows 单独适配。[media_kit](https://pub.dev/packages/media_kit)、[audio_service](https://pub.dev/packages/audio_service)

原生音频库还涉及 libmpv、FFmpeg 等组件，必须核对实际打包版本的许可及对应源码信息，不能仅依据 Dart 包的 MIT 许可判断整个发行包。

### 数据与模块接口

共用层定义曲库访问、元数据读取、播放控制和备份接口；平台路径、Android URI 与系统回调封装在适配层。

- **歌曲**使用稳定 UUID；文件位置作为关联信息保存，不能把路径直接当永久歌曲 ID。
- **标签**采用扁平多标签结构，支持创建、改名、删除及批量添加、移除。
- **规则**保存为带版本号的表达式树：标签、全部满足、任一满足、排除。
- **歌单**区分固定歌曲与顺序的普通歌单，以及保存规则和排序方式的智能歌单。
- **队列**保存歌曲 ID、顺序及当前位置，独立于筛选结果和歌单。

业务层队列可以包含一万首歌，但播放层只为当前歌曲及有限预取创建播放对象，避免 Android 同时打开大量文件句柄。

### 筛选和播放语义

例如：

> （摇滚 或 电子）且（中文 或 日文），排除现场版

通过可视化分组表达，无需用户输入公式。

- 未设置条件时显示全部可用歌曲；“排除”以当前可用曲库为范围。
- 嵌套空组不能保存；相互矛盾的条件正常显示零结果。
- 删除被规则引用的标签时提示影响，并将相关规则标为待修复，不悄悄扩大匹配范围。
- 普通歌单保存当前歌曲和顺序；智能歌单在打开或播放时重新计算。
- 点击播放后生成队列快照。随后修改标签或筛选条件，不改变正在播放的队列。
- 重启应用恢复队列与进度，默认保持暂停。

### 文件访问和恢复

Android 保存系统授予的目录权限及文档 URI，不推导所谓“真实路径”，不申请全盘管理权限。SAF 提供目录及子目录访问能力。[Android 官方文档](https://developer.android.com/training/data-storage/shared/documents-files)

`audio_metadata_reader` 接受文件接口，因此 Android 需要只读文件描述符桥接；这一方案必须在 R1 真机验证，不能假定已经可用。[组件说明](https://pub.dev/packages/audio_metadata_reader)

扫描中断、目录不可访问或授权失效，不得删除已有管理数据。整目录搬家通过重新选择根目录、预览相对路径匹配后恢复；单曲改名通过手动重新关联恢复。

## 3. 开发轮次与每轮交付

**每轮使用一个新对话，只推进一个明确里程碑。** 若验收失败，下一次对话先修复该轮，轮次编号不前移。

| 轮次 | 开发目标 | 手机验收重点 |
|---|---|---|
| **R0：工程与交接底座** | 建立 Git、计划和日志；补齐 Flutter、Windows C++、Android 工具链及组件所需工具；构建双端 Material 3 空壳；建立版本、签名和诊断信息 | USB 调试授权、安装启动、主题切换、版本显示、覆盖安装保留数据 |
| **R1：双端播放技术验证** | 打通目录授权、元数据读取、单曲播放、进度控制和基本后台服务；验证原生依赖与文件句柄生命周期 | 常见格式播放、拖动进度、中文文件名、目录授权保持、锁屏播放、连续切歌 |
| **R2：本地音乐库** | 持久化曲库、多目录递归扫描、增量刷新、取消扫描、基础封面、搜索排序及失联状态 | 扫描目录、重复扫描不重复入库、坏文件不中断扫描、重启保留曲库 |
| **R3：标签管理** | 标签创建、改名、删除；单曲与多选批量操作；数据库关系完整性 | 为歌曲添加多个标签、批量增删、重启保留、删除标签影响正确 |
| **R4：组合筛选** | 可视化嵌套条件、交并差运算、结果数量与预览、播放筛选结果 | 验证指定组合、排除规则、零结果、嵌套编辑、筛选不干扰当前播放 |
| **R5：歌单与队列** | 普通和智能歌单；重命名、删除；队列追加、移除、重排；循环、随机与恢复 | 普通歌单保持固定、智能歌单随标签变化、队列顺序正确、恢复后暂停 |
| **R6：日常使用体验** | 同名 LRC 歌词、可读取的内嵌歌词、封面完善、歌曲信息、睡眠定时、布局与无障碍完善 | 歌词同步、无歌词状态、定时停止、字体缩放、长标题与触控操作 |
| **R7：系统集成与稳定性** | Android 音频焦点、耳机和蓝牙事件；Windows 媒体键、SMTC、托盘；后台和中断恢复加固 | 锁屏持续播放、通知操作、耳机断开、其他应用抢占音频、后台返回 |
| **R8：备份和重新定位** | 管理数据导出与恢复；目录搬家、单曲重新关联；迁移及恢复失败回滚 | 导出恢复、缺失文件保留标签、重选目录、损坏备份被拒绝 |
| **R9：完整验收与首版交付** | 一万首规模验证、缺陷清理、升级回归、许可清单、Windows ZIP 与 Android APK | 从导入到筛选保存播放的完整流程、旧版覆盖升级、最终手机回归 |

R1 是技术关卡：目标手机上的本地目录访问、元数据读取、播放及基本后台能力未通过，不进入后续产品功能轮。

R8 的备份只包含管理数据，不包含音乐。采用版本化导出格式；恢复前自动备份当前数据，恢复操作整体成功或回滚。首版不提供跨设备数据合并。

## 4. 验证方式与通过标准

### 助手负责电脑与工程验证

每轮执行与改动相应的静态检查、自动化测试、双端构建及 Windows 实际运行，保留报告、截图和日志。

重点验证：

- **规则正确性**：交集、并集、排除、嵌套、矛盾条件、标签删除；使用独立集合运算作为预期结果。
- **数据可靠性**：重复扫描、授权失效、扫描取消、缺失文件、数据库升级、备份损坏与恢复回滚。
- **真实播放**：使用可合法分发的固定音频样本验证解码、进度、切歌及错误处理；Windows 使用音频回环采集确认实际输出，不能仅凭进度条认定有声。
- **格式目标**：MP3、FLAC、M4A/AAC、WAV、OGG/Opus；元数据缺失时允许退回文件名，单个坏文件不阻断曲库。
- **性能目标**：一万首测试数据库下，常用标签查询预热后的 P95，Windows 不超过 500 毫秒、测试手机不超过 1 秒；扫描期间保持界面可操作。
- **证据边界**：数据库规模测试与真实文件扫描分别记录；只声明实际执行过的平台和场景通过。

R7 增加锁屏持续播放、连续切歌及内存/文件句柄观察。无法验证的电脑项目明确记录为阻塞或未验证，由助手继续处理。

### 你负责手机体验验收

USB 连接后，助手负责识别设备、安装和抓日志；首次系统授权需要你在手机上操作。

每轮提供约 **5–8 项**清单，每项写明操作和预期结果。你只需反馈：

> 构建号：……  
> 通过：1、2、4  
> 失败：3，实际表现是……  
> 未测试：5

失败时由助手进一步收集日志、定位和修复，不要求你分析技术原因。

状态统一为：

**开发中 → 自动验证通过 → 待手机验收 → 双端通过**

“构建成功”不能替代实际测试，“待手机验收”不能自动变成通过。每轮覆盖安装沿用固定应用标识和本地持久签名，不以卸载清数据掩盖升级问题；密钥不进入 Git。

## 5. 新对话交接与开发日志

首次实施时建立以下文件，作为后续对话的依据：

| 文件 | 职责 |
|---|---|
| `AGENTS.md` | 新对话入口：必读文件、固定工作流程、测试责任、禁止跳过的验收项 |
| `docs/PLAN.md` | 本计划、确认的产品规则、技术选择、轮次和验收标准；变更时记录原因 |
| `docs/HANDOFF.md` | 当前轮次、准确状态、代码提交、构建位置、待验收项目、已知阻塞及下一步 |
| `docs/rounds/Rxx.md` | 每轮追加式开发日志、测试记录、手机反馈、修复过程及最终结论 |

每条开发记录至少包含：

- 日期、轮次、目标与实际变更。
- 关键决定及原因。
- Git 提交、应用版本和构建号。
- 执行的检查、结果及证据位置。
- 已知问题、未验证内容和下一步。

构建产物按轮次保存，包含 APK、Windows ZIP、校验值、测试报告、截图和日志；产物与密钥不提交源码仓库。

每个对话结束前，助手必须更新交接文件。手机尚未反馈就写明“待手机验收”；新对话先吸收反馈、处理失败，再判断能否推进。日志追加更正，不覆盖先前失败记录。

**首次实施**：在新对话附上本计划，要求“执行 R0，并先将完整计划和协作规则写入项目”。
