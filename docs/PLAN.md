# Tag Music：双端本地音乐播放器开发计划

## 1. 已确认的目标与边界

采用 **Flutter + Material Design 3 + 成熟音频组件**，共用界面、标签、筛选及歌单逻辑，分别构建 Windows 和 Android 应用。首版两端数据独立。

- **平台**：Windows 10/11 x64、Android 10 及以上；优先验证当前电脑和你的手机。
- **规模**：一万首以内的本地音乐库。
- **音乐来源**：手动选择多个文件夹，递归扫描；Android 使用系统目录授权。
- **核心功能**：多标签管理、三框组合筛选、临时播放队列、普通歌单、智能歌单。
- **日常功能**：封面、本地歌词、搜索排序、队列编辑、循环与随机播放、睡眠定时、双端后台播放；Android 另有通知及锁屏媒体控制。
- **数据安全**：自定义标签仅存应用数据库；音乐文件不被修改。文件失联时保留标签和歌单关联，支持重新定位。
- **暂不纳入**：云同步、音乐传输、联网歌词、流媒体、均衡器、无缝播放、CUE 分轨及加密音乐解密。

暂用名称 **Tag Music**，简体中文，支持深浅主题。采用本地 Git 管理，默认不创建公开远程仓库；原创代码使用 MIT 许可，第三方组件分别保留其许可要求。

Harmonoid 只作功能参考。其当前 PolyForm Strict 许可没有授予本项目所需的修改、衍生及再分发权利。[许可原文](https://github.com/harmonoid/harmonoid/blob/master/LICENSE)

## 2. 技术结构与关键行为

### 共用代码和平台适配

| 部分 | 确定方案 |
|---|---|
| 界面 | Flutter Material 3；手机底部导航，桌面侧栏导航；共用页面和业务逻辑 |
| 状态与数据 | Riverpod；Drift + SQLite；数据库迁移从第一版开始管理 |
| 播放引擎 | `media_kit` + 音频专用原生库，避免自行实现解码器 |
| 元数据 | `audio_metadata_reader`；封面按需读取、缩略和缓存 |
| Android | Kotlin 封装 SAF 目录访问；`audio_service`、`audio_session` 管理后台播放、通知和音频焦点 |
| Windows | 本地文件系统适配。便携版关闭窗口后在托盘继续播放，托盘提供基本播放控制和退出入口。SMTC、系统媒体键和锁屏媒体卡片暂不安排。 |
| 构建 | PowerShell 7 脚本统一环境检查、测试和打包；工具链及依赖版本在 R0/R1 锁定 |

`media_kit` 已提供双端音频能力；`audio_service` 用于 Android 的后台与系统交互，Windows 单独适配。[media_kit](https://pub.dev/packages/media_kit)、[audio_service](https://pub.dev/packages/audio_service)

原生音频库还涉及 libmpv、FFmpeg 等组件，必须核对实际打包版本的许可及对应源码信息，不能仅依据 Dart 包的 MIT 许可判断整个发行包。

### 数据与模块接口

共用层定义曲库访问、元数据读取、播放控制和备份接口；平台路径、Android URI 与系统回调封装在适配层。

- **歌曲**使用稳定 UUID；文件位置作为关联信息保存，不能把路径直接当永久歌曲 ID。
- **标签**采用扁平多标签结构，支持创建、改名、删除及批量添加、移除。
- **规则**保存为带版本号的三框配置：全部具备、任一具备、排除标签；引用稳定标签 UUID。
- **歌单**区分固定歌曲与顺序的普通歌单，以及保存规则和排序方式的智能歌单。
- **临时队列**在本次运行中维护歌曲ID、条目ID、顺序及当前位置，独立于筛选结果和歌单，不持久化。

业务层队列可以包含一万首歌，但播放层只为当前歌曲及有限预取创建播放对象，避免 Android 同时打开大量文件句柄。

### 筛选和播放语义

例如：

> 全部具备框：[摇滚、中文]；任一具备框：[电子、日文]；排除框：[现场版]

固定三个可视化标签选择框，无需输入公式或编辑嵌套。最终结果为“全部具备框标签的交集”与“任一具备框标签的并集”取并集，再减去“排除框标签的并集”。

- 仅一个包含框非空时使用该框；两个包含框都空时以全部可用歌曲为起点。排除框为空不扣除；三框都空显示全部可用歌曲。
- 同一标签可跨框出现，按公式计算；零结果正常展示。有效编辑立即生效，保存一份当前规则及排序；筛选页与曲库搜索排序独立。
- 删除被规则引用的标签时提示规则及结果范围影响，确认后事务移除各框引用并重算；包含框清空可能恢复全部可用歌曲，已有播放快照保持不变。
- 普通歌单保存当前歌曲和顺序；智能歌单在打开或播放时重新计算。
- 点击播放后生成队列快照。随后修改标签或筛选条件，不改变正在播放的队列。
- 播放状态仅本次运行有效：重启为空队列，默认随机播放、不自动出声；不恢复队列、进度或模式。普通/智能歌单仍持久保存。

### 文件访问和恢复

Android 保存系统授予的目录权限及文档 URI，不推导所谓“真实路径”，不申请全盘管理权限。SAF 提供目录及子目录访问能力。[Android 官方文档](https://developer.android.com/training/data-storage/shared/documents-files)

`audio_metadata_reader` 接受文件接口，因此 Android 需要只读文件描述符桥接；这一方案必须在 R1 真机验证，不能假定已经可用。[组件说明](https://pub.dev/packages/audio_metadata_reader)

扫描中断、目录不可访问或授权失效，不得删除已有管理数据。整目录搬家通过重新选择根目录、预览相对路径匹配后恢复；单曲改名通过手动重新关联恢复。

R8搬家找回继续使用歌曲UUID作为标签/歌单关联。相对路径预览优先，持久化文件SHA-256作为辅助匹配；原文件可读时先留基线，缺基线或内容/内嵌元数据变化时保留路径与人工单曲关联兜底。哈希在后台分批、可取消、流式计算并缓存，不让歌曲列表加载、播放或每次启动等待全库重算。同哈希多份不自动合并歌曲记录；有歧义时先预览确认，不改变异位置同内容仍不合并的规则。

## 3. 开发阶段与交付

R0～R9 编号和核心目标保持不变。阶段启动、Plan → Goal、检查点和换对话规则统一见 [AGENTS](../AGENTS.md)，当前状态只见 [HANDOFF](HANDOFF.md)。阶段内按完整功能组连续实现、集中必要检查并尽早交付体验；整阶段用户验收完成后才能前移。下表是产品路线，不代表已经实现。

| 阶段 | 开发目标 | 手机验收重点 |
|---|---|---|
| **R0：工程与交接底座** | Git、计划/日志、工具链、双端 Material 3 空壳、版本/签名/诊断 | 授权、安装启动、主题、版本、覆盖保留数据 |
| **R1：双端播放技术验证** | 目录授权、元数据、单曲播放/进度、基本后台服务、原生依赖与句柄生命周期 | 常见格式、中文名、进度、授权保持、锁屏、连续切歌 |
| **R2：本地音乐库** | 持久曲库、多目录递归、增量/取消、基础封面、搜索排序、失联状态 | 扫描、去重、坏文件隔离、取消保留、重启持久、搜索输入 |
| **R3：标签管理** | 标签创建/改名/删除、单曲与批量操作、数据库关系完整性 | 多标签、批量增删、重启保留、删除影响 |
| **R4：组合筛选** | 固定三框交并差、数量/预览、规则保留、播放结果 | 指定组合、空框、排除、零结果、删标签联动、不干扰播放 |
| **R5：歌单与队列** | 普通/智能歌单、完整基础编辑、优先待播/移除/重排、四种互斥播放模式 | 固定与动态歌单、顺序/随机历史、重启空队列默认随机不出声 |
| **R6：日常使用体验** | 同名 LRC（内嵌歌词暂缓）、封面完善、歌曲信息、睡眠定时、布局/无障碍 | 歌词同步/缺失、定时停止、缩放、长标题/触控 |
| **R7：系统集成与稳定性** | Windows 便携版托盘后台播放、Android 通知和锁屏媒体卡片精简、OriginOS 原子随身听接入调查，顺带修复标签弹窗与沉浸播放页 | 由用户日常体验。范围见 [R7 执行记录](rounds/R7.md)。 |
| **R8：备份和重新定位** | 管理数据导出/恢复、目录搬家/单曲关联、迁移及恢复失败回滚 | 导出恢复、失联保留标签、重选目录、拒绝坏备份 |
| **R9：完整验收与首版交付** | 一万首规模、缺陷清理、升级回归、许可清单、Windows ZIP/Android APK | 导入→标签→筛选→歌单→播放、旧版升级、最终回归 |

### 交付优先级

- 优先尽快得到个人可用版；先处理后期修改成本高的身份稳定性、旧库迁移、音乐只读与 Android SAF、事务原子性、切歌及 FD 生命周期。已有验证基础复用；独立审查只按明确风险、证据冲突或用户要求启用，不给普通功能组设置例行审查门槛。
- R6 先解决日常 UI 可用性，再做歌词、封面和睡眠定时；R7/R8 仍按计划保留。个人试用与 R9 最终发行门禁是不同目标，不提前宣布阶段通过或删除产品目标。
- R8 保留相对路径预览与人工单曲关联兜底，并按已确认方案用持久化文件 SHA-256 辅助搬家匹配；歌曲身份仍用 UUID，同内容不自动合并歌曲记录。完整计算与确认规则见“文件访问和恢复”。

R1 是目标手机的技术关卡，目录访问、元数据、播放及基本后台能力未过，不进 R2。R8 备份只含管理数据，版本化；恢复前自动备份当前数据，整体成功或回滚，首版不作跨设备数据合并。

### 阶段跨度与内部检查点

2026-10-30 审计决定：不新增阶段或改原核心目标。以下只细化阶段内部的实施/验证顺序；具体任务写进当轮执行计划，未开始的轮次不预建日志。

| 阶段 | 评估与实施顺序 | 依赖 / 收口边界 |
|---|---|---|
| R2 | 持久化/身份/旧目录迁入 → 扫描事务/增量/取消/失联 → 搜索封面/设备体验，分批留证据。当前实现与证据已在 R2，续行优先修复/验收，不重做已验证项。 | 基于 R1 文件/播放入口；现在就留 schema v1、万首合成基准、真实扫描与取消证据。当前输入故障不允许等 R7 修。 |
| R5 | 歌单存储与播放状态依赖相连；先队列状态机/歌曲ID接入，再普通/智能歌单、界面与系统回归；分批检查点，不新增独立阶段。 | 依赖R2歌曲ID、R3标签、R4规则。[R5当前计划](rounds/R5.md#r5-当前执行计划)已确认行为及验收；取消重启恢复，启动默认随机。 |
| R7 | 复用 R1 后台播放、媒体会话和焦点处理，按用户确认的最小范围完成托盘、媒体卡片和两处界面修复。 | 构建双端候选，设备体验由用户负责。系统中断和长时运行专项未纳入本阶段。 |
| R9 | 是全流程与发行收口，规模、升级和许可不能从零开始；先审证据缺口，再最终候选全流程/兼容升级、规模复核和交付清单。 | R2 起性能基线，首次 schema 变化起迁移测试，依赖变化即更新许可核对；最终缺口仍阻塞首版交付，不凭构建成功放行。 |

R0/R1 的底座→技术关卡，R3→R4 的标签→规则，R6 的体验完善、R8 的可逆恢复依赖总体合理。R8 放在数据结构基本成形后不影响早期就验证数据库迁移；R6 才完善歌词/封面不意味着此前可以搁置影响使用的输入或布局缺陷。若实际发现上述阶段仍无法保持可验证交付，再在阶段 Plan 提出重划并请用户确认。

## 4. 验证与质量门禁

### 批次必要检查

开发/协作规则以 [AGENTS](../AGENTS.md#实施与验证) 为准：少量完整页面组或功能链连续实现，批次交付前集中必要检查，优先既有入口；不默认新增测试文件、逐功能测试、全量回归或独立 reviewer。普通界面、布局和交互主要由用户体验，边界问题集中本批处理，反馈按具体问题修复。

| 明确风险变化 | 最小定向检查重点 |
|---|---|
| 数据丢失、事务/删除、数据库迁移 | 原数据/关联保留，旧库升级或失败回滚；不覆盖旧 schema 基线使检查通过 |
| 持久身份、签名/安装身份 | ID 与旧记录关联、覆盖升级保留数据；不卸载/清数据绕过失败 |
| SAF 授权/URI、只读文件与 FD 生命周期 | 实际 URI/授权可用、只读和释放；不推导真实路径或申请全盘权限 |
| 播放并发/异步状态、队列快照 | 对应切歌/旧结果淘汰/快照/FIFO/句柄风险，选与变化直接相关的检查 |
| 原生依赖/打包或许可变化 | 受影响平台包身份/原生输入与许可；公开再分发前闭合 THIRD_PARTY 来源缺口 |

普通共享 UI、公共参数和多个页面本身不触发高风险流程。具体风险需要独立判断时才加 reviewer，写清范围；不机械把全部既有用例带进每批。R7 长时系统组合、R8 恢复/回滚和 R9 最终发行收口仍按各阶段目标确认范围，不用其全面检查阻止当前功能组交付。

### 候选与阶段验收

- 每个可体验功能组交付可运行候选、入口、简短操作/预期和已知缺口；构建在授权范围内执行，安装/启动/前台/设备测试按 [AGENTS](../AGENTS.md#实施与验证) 逐批确认。允许分批、分平台交付体验，不要求每次候选全套检查、双端构建或全部证据收齐后才展示。
- 格式、静态分析或构建集中批次交付前处理，以发现明显编译错误和候选运行阻塞为主。用户反馈后只修复和确认相关问题；不补测试矩阵拖延后续实现。已有命令及覆盖说明见 [项目索引](README.md#验证入口与维护)，入口存在不代表必须全跑。
- MP3、FLAC、M4A/AAC、WAV、OGG/Opus 的固定合法样本沿用；只按相关格式/播放风险选用。实际有声可由用户确认或已授权回环核验，不能仅凭进度宣称有声，不要求每个 UI 候选重录回环。
- 保留万首常用标签查询预热 P95 目标（Windows ≤500ms、目标手机 ≤1s）及扫描时可操作的产品要求；仅在相关性能问题/变化或已确认阶段验收范围测量。真实扫描、合成库、host/debug 和设备 Release 分开记录，不把全性能矩阵作为普通功能交付门槛。
- 实现完成、候选构建/可运行、用户验收分别记录，未执行检查明确未测；阶段概览状态及具体范围依 AGENTS，不把机器通过等同用户通过。阶段最终按已确认功能范围及必要高风险检查提交用户验收，双端通过须有当前候选双端实际结论。
- 产物、哈希、报告、截图及原始日志留 `artifacts/Rxx/`，只存一次；代码检查点与包内 revision 分别记录，不改写旧包身份。每批集中记录与提交，HANDOFF 引用稳定检查点，不追写自身最新 HEAD。
